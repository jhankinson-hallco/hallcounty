# Intune Scripting Pitfalls

## P1 — Bare `powershell.exe` in Portal Install Command

**Symptom:** Script exits with code 1 in < 1 second. No useful log output. Failure occurs before any script logic.

**Cause:** Intune IME is a 32-bit process. Plain `powershell.exe` resolves to 32-bit PowerShell via WOW64. AppX cmdlets or other 64-bit-only modules crash the PS host at the module-load level — before `try/catch` can protect you.

**Fix:** Always use `%SystemRoot%\SysNative\WindowsPowerShell\v1.0\powershell.exe` in the portal install/uninstall command.

**Check:** Does the script's `.NOTES` block document the correct SysNative command? Does the portal actually match it? These can drift independently.

> ⚠️ **Important:** Exit code 1 in < 1 second is NOT exclusively a 32-bit PS crash. After fixing the SysNative command, if the same diagnostic signature persists, see **P18** (PowerShell Constrained Language Mode). Both failures look identical in AppWorkload.log. The differentiator is the diag file: a 32-bit AppX crash produces no diag file AND no `.NET` error output. A CLM failure also produces no diag file if the CLM-restricted call is before the outer try/catch.

## P2 — Stale Default User Hive Mount

**Symptom:** `reg load` returns non-zero on every subsequent run. Script throws. Marker never written. Intune retries indefinitely.

**Cause:** If a script was killed or crashed after `reg load` but before `reg unload`, the mount point persists in `HKEY_USERS`. The next run tries `reg load` and fails because the key already exists.

**Fix:** Always attempt `reg unload` **before** `reg load`, discarding the result:

```powershell
& $script:RegExe unload $script:TempHiveMountPoint 2>&1 | Out-Null
# Now attempt reg load — clean state guaranteed
```

## P3 — PS Registry Provider Blocking Hive Unload

**Symptom:** `reg unload` returns non-zero with "access is denied" or "resource busy."

**Cause:** PowerShell's Registry provider (`Set-ItemProperty`, `Get-ItemProperty`, `New-Item` with `HKLM:\` paths) keeps open handles on registry keys. If those keys are inside a mounted hive, the provider handles prevent `reg unload`.

**Fix:** Use `reg.exe` exclusively for ALL reads and writes to mounted hives. Never mix PS Registry provider operations and hive operations in the same function.

## P4 — `$LASTEXITCODE` Behavior Under `Set-StrictMode -Version Latest`

**Symptom (misconception):** Worry that accessing `$LASTEXITCODE` before any external process call would throw under StrictMode.

**Actual behavior:** PowerShell initializes `$LASTEXITCODE` to `0` at startup. StrictMode Latest does NOT throw on a zero-initialized variable. `$LASTEXITCODE` is safe to check immediately after any `& external.exe` call without pre-initialization.

**Key rule:** `$LASTEXITCODE` resets to `0` at PS startup. It reflects the exit code of the most recent external command (`& executable`). Check it immediately after each external call — do not assume it carries over to nested functions.

## P5 — `Write-Host` vs `Write-Output` in Detection Scripts

**Symptom:** Detection script runs successfully and exits 0, but Intune reports the app as "not installed."

**Cause:** `Write-Host` writes to the Information stream (stream 6), not STDOUT. Intune reads the process's STDOUT. Using `Write-Host` in a detection script produces no detectable output.

**Fix:** Use `Write-Output` in detection scripts. `Write-Host` is never acceptable in detection scripts.

---

## P6 — Here-String Line Endings Depend on Source File Encoding

**Symptom:** Theme file, INI file, or config file generated by a here-string has LF-only line endings instead of CRLF, causing Windows to reject or misbehave with the file.

**Cause:** PowerShell here-strings inherit line endings from the source `.ps1` file. A file saved with LF-only endings (Git on Linux/Mac, or certain editors) produces a here-string with LF-only line endings.

**Fix:** Never use here-strings for files that require CRLF. Use explicit array-join:

```powershell
$Lines = @('line1', 'line2', 'line3')
$Content = ($Lines -join "`r`n") + "`r`n"
```

This is source-file-encoding-independent.

## P7 — `[Slideshow]` Section Without Image Items Causes Black Desktop

**Symptom:** After first login, desktop background is black.

**Cause:** A `.theme` file with a `[Slideshow]` section but no `Item0Path=` or `ImagesRootPath=` value causes Windows to configure a slideshow with zero images on some Windows 11 builds. Result: black desktop.

**Fix:** Remove `[Slideshow]` section entirely unless you are actively configuring a slideshow with real image paths.

## P8 — PersonalizationCSP Lock Screen Is Enterprise/Education-Only

**Symptom:** Lock screen CSP settings applied but have no effect on Windows Pro.

**Cause:** `./Vendor/MSFT/Policy/Config/DeviceLock/...` for lock screen images via PersonalizationCSP requires Windows Enterprise or Education. Windows Pro ignores it.

**Fix for Windows Pro:** Use the ADMX-backed registry policy directly:

```text
HKLM:\SOFTWARE\Policies\Microsoft\Windows\Personalization
  LockScreenImage  = REG_SZ  C:\Path\To\LockScreen.jpg
  NoChangingLockScreen = REG_DWORD  1
```

This works on Windows 10 Pro, Windows 11 Pro, and Enterprise. Does NOT require MDM-enrolled Enterprise license.

## P9 — Default User Hive Changes Do Not Affect Existing Profiles

**Symptom:** Applied wallpaper via Default User hive but existing users still see old wallpaper.

**Cause:** Each user's profile has its own `NTUSER.DAT`. The Default User hive is a template used only when a new profile is **created**. Modifying it after profiles exist has no effect on those profiles.

**Design implication:**

- Default User hive changes = "new users only going forward"
- For retroactive changes = must use HKLM policy (lock screen) or a per-user remediation / scheduled task
- Rollback of Default User hive = only affects future profiles; cannot undo existing profiles

## P10 — 32-bit vs 64-bit Registry Redirection in Detection

**Symptom:** Detection reports "not installed" even though the app is installed, or always reports "installed" even when it isn't.

**Cause:** Detection script running as 32-bit process checks `HKLM:\SOFTWARE\AppName` but WOW64 redirects to `HKLM:\SOFTWARE\WOW6432Node\AppName`. The app installed to the 64-bit path, which is invisible from 32-bit context.

**Fix:** In Intune portal detection script settings, ensure "Run script as 32-bit process on 64-bit clients" is set to `No` for any script checking 64-bit registry or file paths.

---

## P11 — `Test-Path` vs `-LiteralPath` vs `-Path`

**Symptom:** Path check fails or succeeds unexpectedly when paths contain brackets, special characters, or `[` `]`.

**Cause:** `-Path` parameter on `Test-Path`, `Copy-Item`, `Remove-Item`, etc. supports wildcards. Brackets in paths are treated as wildcard character classes. If a path contains `[` or `]`, use `-LiteralPath`.

**Fix:** Use `-LiteralPath` for all explicit, known paths. Only use `-Path` when you deliberately want wildcard expansion.

---

## P12 — `.theme` File Requires Valid `[VisualStyles]` Section

**Symptom:** Theme file applied but desktop background not shown, or theme fails to apply silently.

**Cause:** Windows theme engine requires a `[VisualStyles]` section pointing to a valid `.msstyles` file. A theme file without it or with a path that doesn't exist causes the engine to silently fail.

**Required minimum `[VisualStyles]` section:**

```ini
[VisualStyles]
Path=%SystemRoot%\Resources\Themes\Aero\Aero.msstyles
ColorStyle=NormalColor
Size=NormalSize
AutoColorization=0
```

## P13 — `exit 0` vs `exit 1` — When to Use Each from Install Scripts

- **`exit 0`** — success, or non-critical failure where Intune should not retry (e.g., branding/config where partial success is acceptable)
- **`exit 1`** — deliberate signal to Intune that installation failed and should be retried
- **`exit 3010`** — success, but a reboot is required to complete

For branding/configuration scripts where partial application is tolerable and retry is unlikely to help: always `exit 0`.
For scripts where failure must be communicated to trigger Intune retry: `exit 1` from catch block.

**Never let a `throw` or unhandled exception propagate to PS runtime** — that produces exit code 1 by default but bypasses your logging and marker logic.

## P14 — `$script:` vs Local Scope in Functions

**Symptom:** StrictMode throws "variable not initialized" inside a function that accesses a variable defined at script scope.

**Cause:** Under `Set-StrictMode -Version Latest`, accessing an uninitiated variable throws. Variables defined at script scope with `$script:` prefix are accessible from functions but must use the `$script:` prefix inside those functions too.

**Fix:** Use `$script:VariableName` consistently in both the definition and usage across function boundaries.

---

## P15 — `Remove-Item -Recurse` Timing Issues on Registry Keys

**Symptom:** Sporadic errors removing a registry key tree that "should" be there.

**Cause:** `Remove-Item -LiteralPath $Key -Recurse` can fail if another process has a handle on a subkey. Also, Intune running parallel policy evaluations can create race conditions.

**Fix:** Check existence first, then remove with `-ErrorAction Stop`; wrap in try/catch with a WARN log. Do not retry in a loop.

---

## P16 — Intune Detection Runs More Often Than You Think

Detection scripts are not run once at install time. They run:

- On every Intune sync (every ~8 hours by default)
- On manual "Sync" from Company Portal or Intune portal
- After each installation attempt
- During White Glove pre-provisioning check-in cycles

**Design implication:** Detection scripts and install scripts must be fast and idempotent. A detection script that modifies state or has side effects will cause continuous drift.

---

## P17 — New-Item on Registry Path That Already Exists

**Symptom:** `New-Item -Path $Key -Force` errors even with `-Force`.

**Cause:** If the key already exists and has subkeys, `-Force` re-creation can still fail in some PS versions.

**Fix:** Always check `Test-Path` first; only call `New-Item` if the key does not exist:

```powershell
if (-not (Test-Path -LiteralPath $Key)) {
    New-Item -Path $Key -Force -ErrorAction Stop | Out-Null
}
```

## P18 — PowerShell Constrained Language Mode (CLM) Blocking .NET Type Usage

**Correction (2026-09-04):** Do not treat every static .NET method call as
blocked merely because it uses `::`. Microsoft lists `[guid]` as an allowed
Constrained Language type, and allowed types may have their methods invoked.
Local Windows PowerShell 5.1.26100.9168 testing in a constrained runspace
confirmed both `[guid]::Parse()` and `[guid]::NewGuid()` succeed, while
`[System.IO.Directory]::CreateDirectory()`, `New-Object
System.Diagnostics.ProcessStartInfo`, `New-Object
System.Collections.Generic.List[string]`, and `[Console]::Error.WriteLine()`
are blocked. Evaluate the TYPE against the allowed-type list instead of
banning all static method syntax. Official reference:
https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_language_modes

**Symptom:** Script exits code 1 in < 1 second. 64-bit PS confirmed (SysNative in command). No diag file written. No log file written. Script has no explicit `exit 1`.

**Cause:** Windows Defender Application Control (WDAC) or AppLocker with enforcement mode can place PowerShell into **Constrained Language Mode**. Under CLM, the following are blocked:

- `[System.Collections.Generic.List[string]]::new()` — MethodInvocationException
- `[System.IO.File]::AppendAllText(...)` — blocked
- `[System.IO.Directory]::CreateDirectory(...)` — blocked
- `[System.Text.Encoding]::UTF8` — blocked
- `[datetime]::Now` — blocked
- Any .NET static method call on a type not in the CLM allowlist

With `$ErrorActionPreference = 'Stop'` set at script top and the blocked call placed **outside the main try/catch**, the terminating exception propagates to the PS runtime → exit 1.

**Diagnostic signature:**

- `lpExitCode 1`, process duration < 1 second
- No `C:\Windows\Temp\<ScriptName>_Diag.txt` created (diag write is inside try block)
- No script-authored log file created under IME Logs or legacy log folders
  (logging is inside try block)
- `$PSLanguageMode` returns `ConstrainedLanguage` when tested manually in SYSTEM context

> ⚠️ **IMPORTANT:** This diagnostic signature is IDENTICAL to a script parse error (see **P21**). A parse error also produces exit 1 in < 1 second with no output of any kind — and happens BEFORE any CLM code runs. **Always rule out parse errors first** by running `[System.Management.Automation.Language.Parser]::ParseFile()` on the local source file before assuming CLM is the cause. Misdiagnosing a parse error as CLM leads to rewrites that don't fix the problem.

**Resolution — `System-RemoveBloatwareAppX.ps1`:**

- v1.0.11 failure: CLM blocked `[System.Collections.Generic.List[string]]::new()` outside the try block. Appeared to be the root cause but script ALSO had em dash parse errors (see P21) — both caused exit 1.
- v1.0.12 fix: Full CLM-safe rewrite. Fixed the CLM issue but em dash parse errors remained — script still exited 1.
- v1.0.13 fix: Replaced all em dash characters in string literals with ASCII hyphens. Parse errors resolved. Script now parses cleanly and exits 0 from catch block unconditionally. **Pending White Glove retry verification.**

**Verification:**

```powershell
# Run as SYSTEM (via PsExec64 -s or Intune platform script):
Write-Output $PSLanguageMode
# FullLanguage = no CLM restriction
# ConstrainedLanguage = CLM is active
```

**Fix (if CLM confirmed):**

1. Move ALL initialization code (`[System.Collections.Generic.List[string]]::new()`, etc.) inside the main `try/catch` block
2. Replace all blocked .NET direct method calls with PS cmdlet equivalents — see the CLM-Safe Substitution Reference table in `reference_intune_code_patterns.md`
3. OR: sign the script with a trusted code signing certificate so WDAC grants it Full Language Mode

## P19 — Win32 App Dependency Cascade Failure

**Symptom:** Multiple apps fail without running. Their AppWorkload.log entries show InstallationState = 4 but no SetCurrentDirectory, no lpExitCode, and no install command line logged.

**Cause:** Intune Win32 app dependencies. When an app is configured as a **dependency** of other apps, and the dependency fails, Intune marks ALL dependent apps as failed without attempting to run them. This is by design — if the prerequisite failed, Intune assumes its dependents cannot succeed.

**Key AppActionProcessor.log indicator:**

```text
Marking app with id: <GUID> as executed to prevent execution attempts in this processing cycle since child dependency app with id: <DEPENDENCY-GUID> has failed processing.
```

**This means `<DEPENDENCY-GUID>` is the root failure — fix that, and all cascade failures resolve.**

**Design implication:**

- If App A depends on App B, and App B is ESP-blocking, then App A ALSO behaves as blocking even if not explicitly marked as such — the cascade failure from App B's failure will prevent App A from getting ESP credit
- Every dependency app must be scrutinized as a single point of failure for its entire dependency tree
- Minimize dependency chains during ESP; prefer flat installation order where possible

**Real incident:** 2026-03-27 White Glove failure. `7cb7a96a` (Remove Bloatware - AppX) was the dependency for 8 apps. It crashed with exit 1 (CLM). All 8 cascaded to Error state. 2 of those 8 were ESP-blocking → entire White Glove failed.

## P20 — Missing `-NonInteractive` in Portal Install Command

**Symptom:** Script behaves differently when run from Intune portal vs. manual test. May block or produce unexpected output in headless SYSTEM context.

**Cause:** Without `-NonInteractive`, PowerShell may attempt to use the console for prompts or output, even in SYSTEM context. While this typically doesn't cause an immediate crash, it can produce subtle differences in behavior, especially in scripts that might implicitly prompt for input.

**Fix:** Always include `-NonInteractive` in the portal install command:

```text
%SystemRoot%\SysNative\WindowsPowerShell\v1.0\powershell.exe -ExecutionPolicy Bypass -NoProfile -NonInteractive -File .\ScriptName.ps1
```

**Standard complete command (required flags):** `-ExecutionPolicy Bypass -NoProfile -NonInteractive`

**Observed drift:** It is easy to apply the SysNative fix while accidentally omitting `-NonInteractive`. The script header's documented command is authoritative — always copy-paste from there rather than retyping.

## P21 — Em Dash in Double-Quoted Strings Causes Parse Error in PowerShell 5.1

**Symptom:** Script exits code 1 in < 1 second. No diag file, no log file, no output of any kind. Catch block and all script logic unreachable. Identical diagnostic signature to P18 (CLM block outside try/catch) and P1 (32-bit PS host crash).

**Cause:** The em dash character (`—` U+2014) is encoded in UTF-8 as three bytes: `0xE2 0x80 0x94`. The third byte (`0x94`) maps to the RIGHT DOUBLE QUOTATION MARK (`"` U+201D) in Windows-1252 encoding. PowerShell 5.1 treats `"` (U+201D) as a valid string terminator equivalent to `"` (U+0022). When a UTF-8 script file without BOM is read, PS 5.1 processes the em dash's third byte as a `"` string terminator — prematurely closing any double-quoted string that contains an em dash.

**Effect:** Every em dash in a double-quoted string creates a cascading chain of mismatched string tokens, corrupting the AST of the entire script. The parser exits 1 before any code runs.

**Diagnostic:**

```powershell
# Run on the SOURCE FILE before packaging:
$errors = $null
$tokens = $null
[void][System.Management.Automation.Language.Parser]::ParseFile($scriptPath, [ref]$tokens, [ref]$errors)
if ($errors.Count -eq 0) { Write-Output 'PARSE OK' } else { $errors | ForEach-Object { Write-Output "Line $($_.Extent.StartLineNumber): $($_.Message)" } }
```

Any parse errors = script will NEVER run regardless of CLM, architecture, or exit code handling.

**Key rule: Always run the parser check on the local source file before packaging.** A parse error makes all other fixes irrelevant.

**Fix:** Replace all em dash characters (`—`) in double-quoted string literals with ASCII hyphens (`-`). Em dashes in `<# #>` block comments and `# line comments` are harmless (they're not in string context), but replacing them everywhere is the safest approach.

```powershell
# One-liner fix (run on source file before packaging):
$path = '.\YourScript.ps1'
$content = [System.IO.File]::ReadAllText($path, [System.Text.Encoding]::UTF8)
[System.IO.File]::WriteAllText($path, ($content -replace [char]0x2014, '-'), [System.Text.UTF8Encoding]::new($false))
```

**Why em dashes appear:** They are commonly inserted by AI code generation tools, word processors, or copy-paste from documentation. Always use ASCII hyphens in PS string literals.

**Affected versions:** PowerShell 5.1 (Windows PowerShell). PowerShell 7+ handles UTF-8 without BOM correctly and does not exhibit this behavior.

**Real incident:** `System-RemoveBloatwareAppX.ps1` — all versions through v1.0.12 had em dashes in `Write-DiagLog` and `Add-LogLine` string literals. Each em dash terminated its string early and cascaded 7 parse errors throughout the file. Exit 1 in < 1 second on every White Glove attempt. Initially misdiagnosed as CLM (P18). The CLM fixes in v1.0.12 were correct but irrelevant — the script never parsed at all. Root cause found by running `Parser::ParseFile()` locally and inspecting the token stream: every string token containing an em dash ended prematurely at column = byte offset of the `0x94` byte. Fixed in v1.0.13 (43 em dashes replaced, parse now clean).

## P22 — `[Parameter()]` Decoration Causes ParameterBindingException in PS 5.1 / IME Context

**Symptom:** Script exits with `ParameterBindingException: Parameter set cannot be resolved using the specified named parameters` mid-execution (not at parse time). Log IS written, so CLM and parse errors are ruled out. Failure is at the specific function call line, not inside the function body.

**Documented cause (original, still valid):** In PowerShell 5.1, a function where some parameters have `[Parameter()]` attributes and at least one has NO `[Parameter()]` attribute creates an ambiguous implicit parameter set that the binder fails to resolve. All params must be consistently decorated or none at all.

**Extended finding — confirmed through White Glove deployment (April 2026):** Even with ALL params consistently decorated, `ParameterBindingException` was still thrown on specific functions in PS 5.1 running under the 64-bit SysNative host in SYSTEM/device context (Windows 11 22H2 build 22621.1194). `[CmdletBinding()]` was also added as a defensive measure — it did not resolve the failure.

**What worked:** Converting all functions to **simple functions** (removing ALL `[Parameter()]` attributes and `[CmdletBinding()]` from every function) eliminated the failure entirely. Simple functions use a completely different, minimal binding path — no parameter-set resolution engine, no disambiguation algorithm. Named-parameter calls still bind correctly by name match.

**Critical correction to earlier analysis:** An initial diagnosis claimed the PS 5.1 engine was failing on *every* decorated function in the script. This was **too broad and incorrect**. The same failing run showed `Assert-BudgetSufficient`, `Write-ErrorLog`, and `Get-ExceptionSummary` — all `[Parameter()]`-decorated functions — calling successfully, because the failure was written to the log. The true root cause is narrower: something specific about `Invoke-RemoveC2R`'s signature or call context triggered the failure; the general engine was not broken for all advanced functions. The blanket removal of `[Parameter()]` from all functions is a valid and safe workaround, but it is **not proven root-cause treatment** — it eliminates the entire condition class rather than isolating the specific trigger.

**Lesson:** When diagnosing ParameterBindingException, do not assume all decorated functions in the script are broken. Look at what else ran successfully in the same execution and narrow the scope before drawing broad conclusions.

**Affected pattern (original P22):**
```powershell
function Invoke-InstallerProcess {
    param(
        [Parameter(Mandatory = $true)]
        [string]$FilePath,

        [string[]]$ArgumentList = @(),      # <-- no [Parameter()] — ambiguous parameter set

        [Parameter(Mandatory = $true)]
        [int]$TimeoutSeconds
    )
}
```

**Safe pattern — simple function (no engine involvement):**
```powershell
function Invoke-InstallerProcess {
    param(
        [string]$FilePath,
        [string[]]$ArgumentList = @(),
        [int]$TimeoutSeconds
    )
}
```

**Scope:** Original P22 (mixed decoration) present in `Install-ExeTemplate.ps1` through v1.1.2, RingCentral v1.0.0, Office365 v1.0.0. Extended finding (decoration-consistent functions still failing) observed in `Remove-Office365.ps1` v1.5.2–v1.5.5 across multiple White Glove attempts. Workaround applied in v1.5.6: all functions converted to simple functions.

**Real incidents:**
- `Install-RingCentral.ps1` v1.0.0 — classic mixed decoration. Fixed in v1.0.1.
- `Remove-Office365.ps1` v1.5.2–v1.5.5 — consistent decoration, still failed. `Invoke-NativeProcess` converted to simple function in v1.5.4 (failure moved to next decorated callee). All remaining functions converted in v1.5.6 (failure eliminated).

## P24 — `Split-Path -LiteralPath ... -Parent` Throws ParameterBindingException in PS 5.1 / IME

**Symptom:** Script exits with ParameterBindingException: "Parameter set cannot be resolved using the specified named parameters." Log entry points to a `Split-Path` call, not a function call. Occurs in SYSTEM / IME context even though the syntax looks correct.

**Cause:** PS 5.1 has a known bug where `Split-Path` with `-LiteralPath` and a switch parameter like `-Parent` in the same call fails to resolve the parameter set in some execution contexts. Reproducible issue documented in PowerShell GitHub issue tracker.

**Fix:** Replace all `Split-Path -LiteralPath $x -Parent` with `[System.IO.Path]::GetDirectoryName($x)`. Pure .NET call — no PS parameter binding involved. Behaves identically for absolute paths.

```powershell
# WRONG - throws ParameterBindingException in PS 5.1 IME/SYSTEM context
$dir = Split-Path -LiteralPath $FilePath -Parent

# CORRECT
$dir = [System.IO.Path]::GetDirectoryName($FilePath)
```

**Also affects:** `Split-Path -LiteralPath $x -Leaf` — use `[System.IO.Path]::GetFileName($x)` instead.

**Real incident:** Remove-Office365.ps1 v1.5.7 — confirmed field failure at `$startInfo.WorkingDirectory = Split-Path -LiteralPath $FilePath -Parent` during White Glove. Script had already been hardened against P22 ([Parameter()] decoration), but this separate Split-Path PS 5.1 bug was the next live failure.

## P25 — Pipeline Scalar Unwrap Breaks `.Count` Under `Set-StrictMode -Version Latest`

**Symptom:** Script exits with `PropertyNotFoundException: The property 'Count' cannot be found on this object.` Log entry points to a `.Count` access on what looks like an array. The function that returned the value works correctly when multiple objects are present, but fails when exactly one object is returned.

**Cause:** PowerShell's pipeline unwraps single-element arrays to scalars on output. A function that returns `$list.ToArray()` or `@(...)` internally — when it contains exactly one item — delivers a bare object to the caller, not an array. The object type (e.g., `AppxPackage`, `PSCustomObject`) has no `.Count` property. `Set-StrictMode -Version Latest` makes accessing any missing property fatal.

**This is ONLY a problem when:**
1. The value came through the PS pipeline (function return value, cmdlet output)
2. Exactly one item was returned (zero returns `$null`, two+ returns a real array — both safe)
3. `.Count` is called directly on the returned value without `@()` wrapping

**Fix:** Wrap all `.Count` accesses on pipeline-returned values with `@()`:

```powershell
# WRONG - crashes under StrictMode when function returns exactly one item
if ((Get-AppXOfficePackages).Count -gt 0) { ... }

# CORRECT - @() forces a real array regardless of element count
if (@(Get-AppXOfficePackages).Count -gt 0) { ... }

# Also fix assignment-then-Count:
$results = Get-AppXOfficePackages      # WRONG if .Count follows
$results = @(Get-AppXOfficePackages)   # CORRECT
```

**Not affected:** `.Count` on `System.Collections.Generic.List[T]`, typed `[string[]]` parameters, or array literals assigned directly (`$x = @(1,2,3)`) — these are never unwrapped.

**Real incident:** `Remove-Office365.ps1` v1.5.8 — `Test-AppXOfficeInstalled` called `(Get-AppXOfficePackages).Count` at line 717. OEM device had exactly one matching AppX package. Function returned the bare `AppxPackage` object. StrictMode threw `PropertyNotFoundException`. White Glove failed at AppX detection before any removal ran. Fixed in v1.5.9 by wrapping all three affected `.Count` calls with `@()`.

**Audit checklist:** Search all scripts for `).Count` — any instance where the left side is a function call or cmdlet pipeline output (not a typed parameter or direct `@(...)` literal) needs `@()` wrapping.

## P26 — Direct Registry Property Access Throws Under `Set-StrictMode -Version Latest`

**Symptom:** Script exits with `PropertyNotFoundException: The property 'DisplayName' cannot be found on this object` (or any other registry value name). Log entry points to a line that reads a property off a `Get-ItemProperty` result. Occurs only on some machines, not others — depends on which registry keys are present.

**Cause:** `Get-ItemProperty` returns a `PSCustomObject` whose properties are exactly the registry values present on that specific key. Many registry keys — particularly driver packages, Windows components, and system entries in the Uninstall hive — have no `DisplayName`, `UninstallString`, or other values that the script assumes are universal. Under `Set-StrictMode -Version Latest`, accessing a missing property is fatal.

**This is NOT a null-check problem.** The property doesn't exist at all — `[string]$props.DisplayName` is not a null cast, it's a missing-member access. `IsNullOrWhiteSpace` never runs.

**Fix:** Always guard property access with `PSObject.Properties` before reading the value:

```powershell
# WRONG - throws if the key has no DisplayName value
$displayName = [string]$props.DisplayName

# CORRECT
if (-not $props.PSObject.Properties['DisplayName']) { continue }
$displayName = [string]$props.DisplayName
```

**General rule under `Set-StrictMode -Version Latest`:** Any property access on an object from an external source (registry cmdlets, WMI/CIM, COM, REST deserialization) must be guarded with `PSObject.Properties` or a null-check on the value if the property is optional. Only access properties directly when the type contract guarantees their existence (e.g., typed .NET objects, strongly-typed PS classes).

**Real incident:** `Remove-Office365.ps1` v1.5.9 — `Get-MSIOfficeEntries` read `$props.DisplayName` at line 835 without a guard. On the test device's uninstall hive, one registry key had no `DisplayName` value. StrictMode threw `PropertyNotFoundException` at Iteration 3 of the MSI scan. White Glove failed. Fixed in v1.5.10 by adding `PSObject.Properties` guards for both `DisplayName` and `UninstallString` before either is accessed.

**Audit checklist:** In any loop over registry keys or external object collections, find every direct property access (`$obj.PropertyName`) and confirm either: (a) the type guarantees that property exists, or (b) a `PSObject.Properties` guard precedes it.

## P23 — Marker File Never Written When Install Script Has No Marker Logic

**Symptom:** Detection script always reports "not detected." Intune retries the install on every sync indefinitely. App shows as "Installing" or "Pending" in Company Portal even after the installer ran successfully.

## P27 — `@($genericListVariable)` Throws `ArgumentException` on a `List[T]` Variable

**Symptom:** `System.ArgumentException: Argument types do not match` thrown from a line that looks completely unremarkable — typically `$result = @($someListVariable)` where `$someListVariable` was built with `New-Object 'System.Collections.Generic.List[object]'` (or another generic `List[T]`) and populated via `.Add()`. No type mismatch is visible anywhere in the surrounding code.

**Cause:** In Windows PowerShell 5.1, wrapping a `System.Collections.Generic.List[T]` **variable reference** directly in the array subexpression operator — `@($listVariable)` — can throw this exception. Confirmed via isolated repro to reproduce for a list of plain scalar strings, not only for lists whose elements are themselves arrays (an earlier working theory was that only nested-array elements triggered it; that theory is wrong — a two-element `List[object]` of two bare strings threw the same way). This is distinct from **P25** (pipeline scalar unwrap breaking `.Count`): P25 is about a *single pipeline result* silently losing array-ness; P27 is `@()` itself throwing when given a `List[T]` object directly, regardless of element count or shape.

**What does NOT throw:**

```powershell
$list = New-Object 'System.Collections.Generic.List[object]'
[void]$list.Add('a')
[void]$list.Add('b')

# THROWS: Argument types do not match
$result = @($list)

# SAFE — .ToArray() is the direct, unambiguous fix
$result = $list.ToArray()

# ALSO SAFE — piping through Select-Object/Where-Object first avoids the
# direct-wrap code path entirely, because pipeline output collection uses
# a different internal mechanism than wrapping a variable reference
$result = @($list | Where-Object { $true })
$result = @($list | Select-Object -Skip 1)
```

**Fix:** When converting a `List[T]` (or similar generic collection) to a PowerShell array, always use `.ToArray()`. Never wrap the bare variable in `@(...)`. If the value already came from a pipeline (`$x = SomeCmdlet | Where-Object {...}`), `@()` around that pipeline expression is fine and unaffected — the bug is specifically about wrapping a **variable that already holds a `List[T]` object**, not about pipeline output collection.

**Real incident:** MIS Inventory Navigation Tool (MINT), `Core.Csv.ps1`'s `Read-MintCanonicalHashFile`, 2026-07-22. `$dataRows = @($parsedRows)` (where `$parsedRows` is a `List[object]` of parsed CSV field arrays) threw this exception for every real Getac hash file in the library (175 files), while Desktop/Laptop files parsed without error. The Getac files happened to be single-line (no separate header row to skip), the specific code path that reached the direct-wrap line; other files took a different branch (`@($parsedRows | Select-Object -Skip 1)`, which is pipeline-based and unaffected). Root-caused via an isolated minimal repro rather than guessing from the stack trace, since the stack trace alone pointed only to the wrapping line with no further detail. Fixed by replacing `@($parsedRows)` with `$parsedRows.ToArray()`.

**Audit checklist:** Search for the pattern `@($` followed by a variable name (not a pipeline) — `@\(\$\w+\)` as a regex — in any script that builds a `System.Collections.Generic.List[T]` and later needs a PowerShell array from it. Every direct match is a candidate; replace with `.ToArray()` unless the variable is confirmed to already be a native PowerShell array (`@()`-literal or typed `[string[]]` parameter), which is not affected by this issue.

**Real incident:** `Install-RingCentral.ps1` — `Detect.ps1` referenced `C:\ProgramData\RingCentral\install.marker` but the install script had `$script:DetectionPath = ''` and no marker write logic. Installer ran successfully, returned exit 0, but detection always returned "not detected." Fixed in v1.0.2.

## P28 — `.GetNewClosure()` Breaks Live `$script:`-Scoped Variable/Property Access

**Symptom:** A WinForms (or other delayed/event-driven) scriptblock that reads or sets a `$script:`-scoped variable throws when the event actually fires — commonly `The property 'X' cannot be found on this object. Verify that the property exists and can be set` (if the target is a non-null object of the wrong apparent shape) or `You cannot call a method on a null-valued expression` (if the target reads back as `$null`). The exact same `$script:` reference works fine in code that runs synchronously, in the same call stack, right after the variable was set — the bug only appears once the scriptblock is invoked LATER, after the function that created it has already returned (a button click, a `CheckedChanged` event, a timer tick, and so on).

**Cause:** `.GetNewClosure()` captures the scriptblock's LOCAL variables as a bound snapshot so they survive after the defining function returns — this part works correctly and is well-documented. What is not obvious: it does **not** correctly preserve live resolution of `$script:`-prefixed variable/property access from inside that closure. A `$script:MyState.SomeProperty = $value` line inside a `.GetNewClosure()`'d scriptblock resolves `$script:MyState` against the closure's own isolated captured-variable set rather than dynamically walking up to the real script scope — so it comes back unset/null even though `$script:MyState` unquestionably exists and is correctly populated in the real script scope at the moment the event fires.

**This is a different failure mode from the nested-function scope bug (see the entry script's own v1.0.2 hotfix history in `MIS Inventory Navigation Tool.ps1`'s change log for MINT):** that one is about a `function Name {}` defined inside another function vanishing once the outer function returns. This one is about `.GetNewClosure()` specifically mishandling `$script:` scope resolution for variables/properties referenced directly inside the closure body. Both surface the same way — code that works when called synchronously breaks when invoked later as an event handler — but the fix is different.

**Fix:** Do not use `.GetNewClosure()` on a scriptblock that needs to read or write `$script:`-scoped variables or their properties. A PLAIN scriptblock (no `.GetNewClosure()`) correctly resolves `$script:` references even when invoked much later as a delayed event handler — confirmed via isolated repro. If the scriptblock also needs a specific control or value that is not itself `$script:`-scoped, prefer routing it through a `$script:`-scoped state container (e.g. one `$script:MyTabState` `PSCustomObject` holding every control the tab's handlers need) rather than closure-capturing local variables by name, and use the WinForms automatic `$this` variable (the control that raised the event) for the sender's own properties (e.g. a `CheckBox`'s `.Checked` state) instead of closing over the control variable itself.

```powershell
# WRONG — .GetNewClosure() breaks $script:MyState resolution once the
# defining function has returned and this fires later as an event handler
$checkBox.Add_CheckedChanged({
    $script:MyState.Flag = $this.Checked   # throws or silently no-ops
}.GetNewClosure())

# CORRECT — plain scriptblock, $script: resolves correctly at invocation time
$checkBox.Add_CheckedChanged({
    $script:MyState.Flag = $this.Checked   # works
})
```

**Real incident:** MIS Inventory Navigation Tool (MINT), `Tab.Search.ps1`'s "Show Decommissioned Devices" checkbox handler, 2026-07-22. Jeremy reported a real crash (full .NET unhandled-exception dialog) on first use: `The property 'ShowingDecommissioned' cannot be found on this object`. The handler was the only place in the file using `.GetNewClosure()`, specifically to capture several `DataGridView`/`Button` control variables — all of which were already available on `$script:MintSearchState` anyway. Root-caused via an isolated two-line repro (a `$script:`-scoped `PSCustomObject`, a `.GetNewClosure()`'d scriptblock setting a property on it, invoked after the defining function returned) rather than guessing from the stack trace. Fixed by removing the only `.GetNewClosure()` call in the file and rewriting the handler as a plain scriptblock reading `$this.Checked` and every control via `$script:MintSearchState`.

**Audit checklist:** Search any WinForms/event-driven PowerShell script for `.GetNewClosure()`. For each hit, check whether the scriptblock body references `$script:` anywhere. If it does, remove `.GetNewClosure()` and verify the scriptblock still has everything it needs either via `$this`/event args or via a `$script:`-scoped state container — do not assume `.GetNewClosure()` is required just because the scriptblock is registered as a delayed event handler.

## P29 — `return $array` Collapses a 0-Element Array to `$null` Across a Function Boundary

**Symptom:** `System.Management.Automation.ParameterBindingValidationException: Cannot bind argument to parameter 'X' because it is null` thrown from a completely unrelated-looking call site — typically a WinForms handler that calls `$var = Get-SomeAccessorFunction` and then passes `$var` straight into another function whose parameter is typed (e.g. `[string[]]`) with `[AllowEmptyCollection()]` but not also `[AllowNull()]`. Nothing in the immediate code looks wrong; the accessor function "obviously" returns an array.

**Cause:** In Windows PowerShell 5.1 (and PowerShell generally), a bare `return $array` — with no leading comma — sends `$array` through the normal pipeline-output unwrapping behavior, exactly like any other unwrapped pipeline emission. When `$array` has exactly 0 elements, unwrapping it emits **zero objects** into the output stream, not one object that happens to be an empty array. A caller that captures the result with `$result = Get-Thing` therefore gets `$null`, not an empty array — even though the function's own local variable was a real, correctly-initialized empty array right up until the `return` statement. This is the return-statement counterpart to the pipeline auto-unwrapping most PowerShell users already know about for `Write-Output $array`; it is easy to forget it applies to `return` too, especially when the function has an early-return branch elsewhere that correctly uses `return ,$array.ToArray()` (e.g. for an error/not-found case) and a LATER "normal" return that was written without the comma out of habit.

**Fix:** Any function whose contract is "always returns an array, even if empty" must comma-wrap every return path: `return ,$array`. This applies whether the array comes from a `.ToArray()` call, a property access (`return ,$object.SomeArrayProperty`), or any other array-typed expression. A caller receiving the result should still be able to trust `.Count` works and iteration is safe even when the function legitimately has nothing to return — that contract silently breaks without the comma specifically at the 0-element boundary (1+ element arrays are unaffected; the bug is invisible in the common/populated case, which is exactly why it survives testing until the collection is genuinely empty in production).

```powershell
function Get-ThingsInternal {
    # WRONG — collapses to $null when $script:Index.Things has 0 elements
    return $script:Index.Things

    # CORRECT — always returns a real array, even when empty
    return ,$script:Index.Things
}
```

**Real incident:** MIS Inventory Navigation Tool (MINT), `Core.Inventory.ps1`, 2026-07-23. `Get-MintInventoryFiles`, `Get-MintModelMap`, `Get-MintDepartmentMap`, and `Get-MintGroupTagChoices` all used the bare `return $script:MintInventoryIndex.<Property>` form. `Get-MintGroupTagChoices` crashed Jeremy's real Batch Edit feature with `Cannot bind argument to parameter 'GroupTagChoices' because it is null`, because `variables\grouptags.csv` did not exist yet on the live filestore, so `GroupTags` was a legitimately empty (not missing/error) array — the exact 0-element case this bug requires. The other three accessors had the identical latent bug but had not yet crashed anything, only because their backing collections (hash files, models, departments) happened to always have at least 1 element in every environment tested so far; fixed all four together rather than only patching the one that had visibly crashed. Root-caused by tracing the exception back past the immediate `[AllowEmptyCollection()]`-without-`[AllowNull()]` parameter (a red herring on its own — that parameter constraint is correct and intentional) to where the `$null` actually originated.

**Audit checklist:** For any function whose job is "return the current value of a collection" (an index accessor, a cached-list getter, a filtered-subset helper), check every `return` statement for a bare `return $arrayExpression` with no leading comma. Confirm via a live test that calls the function when the backing collection has 0 elements and asserts the result `-ne $null` and `.Count -eq 0` — do not just confirm it works when the collection is populated, since that is precisely the case this bug hides behind.

## P30 — `[string]$Param = $null` Is Coerced to `""` on Bind, Defeating a "`$null` Means Leave Unchanged" Convention

**Symptom:** A worker function with an optional `[string]$OverrideX = $null` parameter, gated by `if ($null -ne $OverrideX) { use override } else { use existing value }`, ALWAYS takes the override branch — even on calls that never supply `-OverrideX` at all. The field it controls gets silently overwritten to blank on every single call, including ones that were specifically designed and tested to leave it alone.

**Cause:** In Windows PowerShell 5.1, a `[string]`-typed parameter is coerced through the string type converter at the moment it is bound — including when the bound value is its own `$null` default, and including when a caller explicitly passes `$null`. The result is a real, non-null `System.String` instance holding `""`, not an actual null reference. `$null -ne $OverrideX` is therefore **always true** — for a genuinely-omitted call, an explicitly-`$null`-passed call, and a real empty-string override, all three look identical to the function body. There is no way to make PowerShell preserve an actual `$null` inside a `[string]` parameter slot once binding has happened, for either the default-value path or the explicit-argument path — `[AllowNull()]` only stops the binder from REJECTING a null argument; it does not stop the string type converter from replacing it with `""`.

**Fix:** Do not test the parameter's bound VALUE to distinguish "was this supplied." Test `$PSBoundParameters.ContainsKey('OverrideX')` instead — this reflects whether the caller named the parameter at all, independent of what the string coercion did to whatever value they passed. Callers that want a genuine "clear this field" override must supply the parameter (an empty string is then a legitimate, intentional override value); callers that want "leave unchanged" must OMIT the parameter entirely — via conditional splatting (build a hashtable, only add the key when a real override is intended, call with `@hashtableVariable`), never by explicitly passing `-OverrideX $null`, since that is bound identically to `-OverrideX ''` once coercion happens.

```powershell
function Set-ThingValue {
    param(
        [Parameter(Mandatory = $true)] [object]$Target,
        [Parameter(Mandatory = $false)] [AllowNull()] [string]$OverrideX = $null
    )
    # WRONG — $OverrideX is "" (not $null) on every call, omitted or not;
    # this branch fires unconditionally and silently blanks the field.
    $valueToWrite = if ($null -ne $OverrideX) { $OverrideX } else { $Target.X }

    # CORRECT — reflects whether -OverrideX was actually named by the caller
    $valueToWrite = if ($PSBoundParameters.ContainsKey('OverrideX')) { $OverrideX } else { $Target.X }
}

# Caller: conditional splatting, not an always-present named argument
$writeParams = @{ Target = $target }
if ($wantsOverride) { $writeParams['OverrideX'] = $newValue }   # '' is a valid real override
Set-ThingValue @writeParams
```

**Real incident:** MIS Inventory Navigation Tool (MINT), `Tab.Search.ps1`'s `Invoke-MintFixImportFormatSingleFile`, discovered 2026-07-24 while building D-058 (a new "Remove All Assigned Users" Batch Edit mode). The function's pre-existing `-OverrideGroupTag` parameter (shipped in D-050, 2026-07-23) used exactly the broken `$null -ne $OverrideGroupTag` pattern. This meant the ALREADY-SHIPPED, ALREADY-USED standalone "Fix Import Format" button — which has always called this function with zero override arguments, by design, specifically to leave Group Tag untouched — had been silently wiping every fixed file's Group Tag to blank on every single use since the day it shipped, including Jeremy's real 175-file production run (the one that motivated D-051's report-writer retry fix). The bug escaped detection through five subsequent rounds of regression testing because the existing test fixture for "fix with no override" happened to use a sandbox file whose Group Tag already started blank — `[string]::IsNullOrEmpty($result.GroupTag)` is trivially true whether the value was correctly preserved or incorrectly wiped, so that assertion could never have caught it. Found via a live isolated repro built specifically to verify the NEW D-058 code path (which reintroduced the same pattern for a second parameter, `-OverrideAssignedUser`) BEFORE trusting it, not by suspecting the pre-existing code. Fixed both parameters together in the one function, switched the calling code (Batch Edit's per-file loop) to conditional splatting, and corrected the masking test fixture to start with a real non-blank Group Tag so the assertion can actually fail if this regresses.

**Audit checklist:** Search for the pattern `[string]$\w+ = \$null` in any parameter block, then check every `if ($null -ne $ParamName)` (or `-eq $null`) guard against that same parameter — every match is broken the same way. Also check every call site: an always-present named argument (`-OverrideX $someVarThatMightBeNull`) reintroduces the bug even after the function itself is fixed to use `$PSBoundParameters.ContainsKey()`, since a coerced `""` is a real, present value the ContainsKey check will happily honor as "supplied." When writing a NEW regression test for a "no override leaves the field unchanged" code path, always seed the fixture with a genuinely non-blank/non-default starting value for that field — a blank-to-blank round-trip cannot distinguish "correctly preserved" from "silently wiped," which is exactly how this bug survived five prior rounds of testing undetected.

## P35 — `return ,$array` (P29's Own Fix) Breaks a Direct Pipe Into `Select-Object -ExpandProperty`

**Symptom:** `Select-Object : Property "X" cannot be found` thrown from a call site that looks completely correct — `Get-SomeAccessorFunction | Select-Object -ExpandProperty X -Unique` — even though every element of the collection genuinely, verifiably has a property named `X` (confirmed via `(Get-SomeAccessorFunction)[0].X` working fine in isolation). Often wrapped in a defensive `try/catch` that silently swallows the exception to an empty fallback array, so the ONLY visible symptom is a list/dropdown that never populates with real data — no error ever surfaces to the user or the log.

**Cause:** A function following the P29 convention (`return ,$array`, the leading comma preventing a 0- or 1-element array from collapsing to `$null`/a scalar across the function-return boundary) emits its array as **one single pipeline object**, not as separately-enumerated elements — that is the entire point of the leading comma. This is fine for a caller that assigns the result to a variable first (`$x = Get-Thing; $x | ...` enumerates normally once piped from a variable). But when the FUNCTION CALL ITSELF is used as the immediate left-hand side of `|` (`Get-Thing | Select-Object -ExpandProperty X`), `Select-Object -ExpandProperty` receives that one wrapped-array object and looks for property `X` **on the array itself** (which has no such property — arrays have `Count`, `Length`, etc., not your element's properties), not on each element inside it. Confirmed via live isolated testing under real Windows PowerShell 5.1 that this reproduces identically for a 1-element array and a 2+-element array (not a "collapses only when empty" issue like P29 — this is a distinct, separate failure mode caused by the SAME leading-comma fix), and reproduces even with an intermediate `Where-Object` stage between the function call and `Select-Object` (`Get-Thing | Where-Object {...} | Select-Object -ExpandProperty X` fails the same way — `Where-Object`, when given one wrapped-array object, evaluates its filter against the array as a whole, which is not a fix).

**Fix:** Never pipe a P29-style function call directly into `Select-Object -ExpandProperty` (or anything else that needs per-element enumeration). Assign the function's return value to a variable FIRST, then pipe the VARIABLE:

```powershell
function Get-ThingsInternal {
    return ,$script:Index.Things   # correct per P29, but now see below
}

# WRONG — throws "Property 'X' cannot be found", even though every
# element genuinely has .X, even through an intermediate Where-Object
$names = Get-ThingsInternal | Select-Object -ExpandProperty X -Unique
$names = Get-ThingsInternal | Where-Object { $_.Active } | Select-Object -ExpandProperty X -Unique

# CORRECT — assign first, then pipe the variable
$things = Get-ThingsInternal
$names = $things | Select-Object -ExpandProperty X -Unique
```

**Real incident:** MIS Inventory Navigation Tool (MINT), discovered 2026-08-07 after Jeremy reported "the dropdowns are not populating with entries from the CSV" on the newly-shipped Import Files tab. Root-caused via a series of live isolated repros (not assumed from reading the code) that progressively narrowed from "the dropdown is empty" to the exact mechanism above. The SAME broken pattern — `Get-MintModelMap | Select-Object -ExpandProperty ModelName -Unique`, always wrapped in a `try/catch` that silently fell back to an empty array — turned out to already exist in three OTHER places across the codebase, all silently affected the same way: Batch Extract's own Model dropdown (apparently broken since it shipped, never noticed live because a fallback list of "already in use" values usually had enough real data to work with in practice, masking the missing configured-choices half), and two shared dialogs (a Batch Edit Model list, a Move-to-Model-Folder existing-models list). All four fixed together once the pattern was recognized, rather than only patching the one Jeremy happened to notice.

**Audit checklist:** Grep for `Get-\w+ \| Select-Object -ExpandProperty` (and the same pattern with an intermediate `Where-Object`/`ForEach-Object` stage) across any codebase using the P29 `return ,$array` convention. For each match, confirm the source function actually uses `return ,` (a function using a bare `return $array`, or one that never risks 0/1-element collapse, is not affected the same way — though a bare `return $array` has its OWN P29 problem instead). When writing a regression test for "does this dropdown/list populate from configured data," always seed the backing data source with real entries and assert the POPULATED case explicitly — a test that only exercises the "in-use fallback" values, or that only checks the collection's own `.Count` rather than actually consuming it the same way the production code does, can pass cleanly while this bug is present, exactly how it went undetected in Batch Extract.

## P36 — CLM-Safe Timed Process Supervision Has Exit-Code Traps

**Symptom:** A wrapper that launches a child process works in FullLanguage but
fails under Constrained Language Mode with `Cannot invoke method. Method
invocation is supported only on core types in this language mode.`

**Cause:** Direct method calls on `System.Diagnostics.Process` objects, such as
`$process.WaitForExit(...)`, `$process.Refresh()`, and sometimes handle-touch
patterns, are blocked under CLM.

**Fix pattern:** Use a split implementation:

```powershell
if ($ExecutionContext.SessionState.LanguageMode -eq 'ConstrainedLanguage') {
    # Do not use -NoNewWindow here if the parent may have redirected streams.
    $process = Start-Process -FilePath $exe -ArgumentList $args -PassThru -WindowStyle Hidden
    Wait-Process -Id $process.Id -Timeout $timeoutSeconds -ErrorAction Stop
    $exitCode = $process.ExitCode
}
else {
    $process = Start-Process -FilePath $exe -ArgumentList $args -PassThru -NoNewWindow `
        -RedirectStandardOutput $stdout -RedirectStandardError $stderr
    $null = $process.Handle
    $completed = $process.WaitForExit($timeoutSeconds * 1000)
    $process.Refresh()
    $exitCode = $process.ExitCode
}
```

**Important:** A pure `Wait-Process` rewrite can lose exit-code capture when the
child process has redirected stdout/stderr. Also, under simulated CLM,
`Start-Process -NoNewWindow` produced blank `.ExitCode` when the parent process
had redirected streams; `WindowStyle Hidden` preserved the exit code.

**Real incident:** `System-RemoveBloatwareAppX.ps1` v1.0.12 failed under a
sterile CLM harness after launching the child but before waiting/enforcing
timeout. v1.0.13 fixed this with the split supervision path above and passed
FullLanguage and CLM success, nonzero exit, and timeout harness scenarios.

## P37 — Wrapping (or Inlining) a P29-Style `return ,$array` Call in `@(...)` Double-Wraps It, Collapsing Multi-Element Results to a Count of 1

**Symptom:** A function built to the P29 convention (`return ,$array`, comma-protected so 0/1/N-element results all survive the function boundary) appears to work when exactly one element exists, but a caller's `@(Get-Function).Count` — or a caller's `foreach ($x in @(Get-Function))` / `foreach ($x in Get-Function)` with no intermediate variable — silently reports `Count: 1` and iterates exactly once regardless of how many real elements the function actually found. On the single iteration, the loop variable's properties read as if PowerShell's member-enumeration-across-collection behavior had concatenated every real element's values into one string (e.g. two elements named `Alice` and `Bob` read back as a single `Name` of `'Alice Bob'`), because the loop variable is actually the WHOLE inner array, not one element of it.

**Cause:** `return ,$array` puts exactly ONE object onto the pipeline — the array itself, protected from PowerShell's normal unwrap-and-enumerate pipeline behavior. That is what correctly preserves the 0-element case (P29's whole point). But it also means the function's entire output, from the caller's perspective, is a single pipeline item. Wrapping that single item in `@(...)` at the call site produces a new outer array containing exactly that one item — which is itself the inner array — i.e. `@(the_array)`, a length-1 wrapper whose sole element is the real array. `.Count` on the outer wrapper is therefore always 1, never the true inner count. The same double-wrap happens with NO explicit `@()` at all: `foreach ($x in Get-Function)` (a bare function call as the foreach source expression, no intermediate variable) exhibits the identical collapse — proven live, not just with `@()`. This is a distinct, stricter trap than P35 (which is about piping a P29-style call into `Select-Object -ExpandProperty`): P37 breaks plain `.Count` and `foreach`, the two most basic ways a caller would consume the result.

**This is NOT a P29 bug in the function being called.** The function's own `return ,$array` is correct per P29. The bug is entirely on the CALLER side, in how the comma-protected single-pipeline-item result gets consumed.

**Fix:** The only safe pattern is direct assignment to a plain variable FIRST, with no `@()` and no inline function call in the `foreach`/`.Count` expression. Assignment alone correctly unwraps the comma-protected item back into the real array, for 0, 1, and N elements alike:

```powershell
function Get-ThingsInternal {
    $things = @()
    # ... populate $things with 0, 1, or many items ...
    return ,$things   # correct per P29
}

# WRONG — @() wrap double-wraps; Count is always 1 regardless of true count
$count = @(Get-ThingsInternal).Count
foreach ($thing in @(Get-ThingsInternal)) { ... }   # exactly 1 iteration, always

# ALSO WRONG — no @(), but still a bare function call as the foreach source;
# same double-wrap, same single bogus iteration
foreach ($thing in Get-ThingsInternal) { ... }

# CORRECT — assign to a variable first, then use the variable
$things = Get-ThingsInternal
$count = $things.Count          # true count: 0, 1, or N
foreach ($thing in $things) { ... }   # true per-element iteration
```

**Real incident:** Barracuda NAC VPN project, `Install-BarracudaNACVPN.ps1`, 2026-09-08. While adding `Get-TrustedBarracudaEntries` (a new P29-style registry-scan function) and its callers `Test-BarracudaExpectedVersion`/`Get-UnexpectedBarracudaVersions`, the initial implementation called it via `foreach ($Entry in @(Get-TrustedBarracudaEntries))` in both callers, and a separate caller in MAIN assigned via `$UnexpectedVersions = @(Get-UnexpectedBarracudaVersions)`. A minimal isolated repro (two known synthetic items, `Get-TwoItemArray`) caught it immediately: `@(Get-TwoItemArray).Count` reported `1`, and a `foreach` over it produced one iteration whose `.Name` read `'Alice Bob'` — proof the loop variable was the whole 2-element array, not one element. The same repro also proved the bare-inline `foreach (... in Get-TwoItemArray)` (no `@()` at all) was equally broken. Fixed by removing every `@()` wrap and every inline function-call-as-foreach-source, replacing each with a two-step assign-then-consume pattern. Re-verified against real registry data (0 results, correct) and synthetic 3-element data with 2 non-matching entries (correctly reported `Count: 2` with both real entries listed, not collapsed to 1) before this ever reached a live endpoint.

**Audit checklist:** In any codebase using the P29 `return ,$array` convention, grep for `@(FunctionName` and for `foreach ($\w+ in FunctionName` (a bare function call, not a variable, as the foreach source) where `FunctionName` is known to use `return ,`. Every match is broken the same way. When writing a NEW regression test for a P29-style function's caller, always exercise the 2+-element case explicitly — the 0- and 1-element cases can both appear to "pass" under this bug (0 stays 0-ish depending on the exact wrap; 1 stays 1, masking the double-wrap entirely), so only a genuine multi-element test can catch it.
